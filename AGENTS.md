- KYB Onboarding Invites store only a SHA-256 hash of the link token and are registered server-side via the `register-with-invite` function (email always taken from the invite); never call signUp from the client for invites. Why: the invited email must be impossible to change.
- Successful invite registration must attempt password sign-in and open onboarding, with sign-in fallback instead of confirmation-email UI. Why: invite-created accounts are already confirmed server-side.
- The onboarding approval gate must allow authenticated exporters to access their notification history without unlocking invoice access. Why: pending applicants need to read reviewer feedback.
- Staff visibility of an exporter (and its directors/documents) goes through `v2_can_view_exporter`: BDs see only exporters they created/invited; KYB packs and sensitive-field reveals go through the `exporter-pack` function. Why: one ownership rule, every reveal/download audited.
- Shared KYB PDF and ZIP links go through a token-hashed download function which checks revocation on every request; storage-signed URLs remain server-only and each share uses a unique private object. ZIP link creation uses a separately audited ready state without email delivery. Why: storage signatures alone cannot provide immediate per-link revocation, and downloadable links must not depend on email verification.
- Pack sharing invokes the common app-email sender server-side; the sender validates the persisted pack event and rebuilds its email data. Why: clients cannot spoof pack links or bypass approval and recipient constraints.
- Application activity is captured by database triggers in an immutable application-specific stream, preserving source timestamps and source IDs. Why: lifecycle, document and review paths cannot silently bypass the Activity tab.
- Onboarding submission alerts originate from submission-timestamp transitions; each recipient notification dispatches one authenticated, server-validated app email. Why: autosaves stay quiet, reviewers are deduplicated, and client-supplied recipients cannot expose another application.
- Notification type constraints must accept every type emitted by application triggers. Why: a rejected notification insert rolls back the exporter submission that generated it.
- KYB exports account for every upload, disclose security-scan exclusions except explicit upload-specific presentation omissions retained in audit, and fail on unreadable eligible attachments; original PDF pages are framed with clear footer space. Why: packs must not lose documents or obscure ID content, and presentation exceptions never clear security flags.
- Staff full-pack downloads use the server-side bundle mode to ZIP the full PDF with numbered, type/person-labelled original files; shared email PDFs retain full mode. Why: download packaging must not break PDF sharing or duplicate client-side assembly.
- Generated shared packs use a dedicated private storage bucket with no client read/write policies; persisted links retain their bucket for revocation cleanup. Why: source-upload MIME restrictions must remain intact, and stored shared files must not expose raw storage signatures to staff browsers.
- One-off onboarding activation exemptions use authenticated Super Admin review records; resolution exceptions must be application-scoped and single-use without changing document scan or invoice gates. Why: an activation waiver must not become a reusable platform-wide compliance bypass.
- Copied ZIP share links use a public static branded landing page with the token only in the URL fragment; social metadata is generic and contains no application data, and downloads still go through the audited revocation gate. Why: WhatsApp crawlers need initial HTML metadata but must not fetch confidential documents or receive the bearer token.
