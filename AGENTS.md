- KYB Onboarding Invites store only a SHA-256 hash of the link token and are registered server-side via the `register-with-invite` function (email always taken from the invite); never call signUp from the client for invites. Why: the invited email must be impossible to change.
- Successful invite registration must attempt password sign-in and open onboarding, with sign-in fallback instead of confirmation-email UI. Why: invite-created accounts are already confirmed server-side.
- The onboarding approval gate must allow authenticated exporters to access their notification history without unlocking invoice access. Why: pending applicants need to read reviewer feedback.
- Staff visibility of an exporter (and its directors/documents) goes through `v2_can_view_exporter`: BDs see only exporters they created/invited; KYB packs and sensitive-field reveals go through the `exporter-pack` function. Why: one ownership rule, every reveal/download audited.
- Shared KYB PDF links go through a token-hashed download function which checks revocation on every request; storage-signed URLs remain server-only and each send uses a unique private object. Why: storage signatures alone cannot provide immediate per-link revocation.
- Application activity is captured by database triggers in an immutable application-specific stream, preserving source timestamps and source IDs. Why: lifecycle, document and review paths cannot silently bypass the Activity tab.
- Onboarding submission alerts originate from submission-timestamp transitions; each recipient notification dispatches one authenticated, server-validated app email. Why: autosaves stay quiet, reviewers are deduplicated, and client-supplied recipients cannot expose another application.
